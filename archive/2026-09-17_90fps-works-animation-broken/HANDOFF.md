## 2. 参考补丁的结论(来源:`G:\Ra3 BattleField\docs\RA3-60FPS-PATCH-ANALYSIS.md`)

- 社区补丁 = 代理 `xinput1_3.dll`(DLL 劫持)+ **另一份 2012 构建的主程序**;只认那份主程序的写死偏移。
- 它改 6 处:客户端帧率全局 30→60、逻辑调度批次块、阶段插值块、粒子生成 `fmul`、粒子过期 `imul`、脚本模型视觉步长 `addss`。
- **逻辑帧率(15)没动**,所以游戏速度不变。

### 引擎的帧时序(2009 构建地址)

| 项 | 地址 | 说明 |
|---|---|---|
| 逻辑帧率 | `0xCAF9D0` = 15 | sim 每秒推进多少帧 |
| 客户端帧率 | `0xCAF9D4` = 30 | 渲染 / 客户端每秒帧数 |
| 客户端帧/毫秒 | `0xCDBC5C` | = 帧率 × 0.001,启动时由 `0xBB3101` 算出;全镜像 10 处 `fmul` 用它 |
| 客户端每帧处理 | `sub_6027D0` | 阶段号 `obj+0x58`(1..6)、插值系数 `obj+0x60`、比值 `obj+0x5C`、FPS 统计 `obj+0x68/+0x6C/+0x70` |
| 逻辑帧驱动 | `sub_616130` | 每客户端帧按 `r = 客户端帧率 ÷ 逻辑帧率` **批量补跑阶段**,末尾把插值系数写成 `阶段 ÷ 6` |
| 阶段门 | `sub_5FFAD0` | `阶段 == 6 ÷ r`(r ≥ 6 时用 1);被别处当「本逻辑帧的第几阶段」判据 |

**6 个阶段 = 两个逻辑帧之间的插值分辨率**。原版 r = 2 ⇒ 每客户端帧跑 3 个阶段;r = 4(60 帧)⇒ 整数除法 `6 ÷ 4 = 1`,每帧只跑 1 个阶段 ⇒ 6 帧才凑一个逻辑帧 ⇒ **游戏会慢到 2/3 速**。这就是必须改批次的原因。

### ★参考补丁的两个缺陷(我们要修掉)

1. **插值系数被覆盖**:补丁改了 `sub_6027D0` 里算系数的那段,但 `sub_616130` 在**批次循环之后**又把系数写成 `阶段 ÷ 6`(原版代码没动)。
   ⇒ 60 帧下每逻辑帧四帧的系数实际是 `1/6 → 3/6 → 4/6 → 1`(不均匀),而不是补丁想要的 `0.25 / 0.5 / 0.75 / 1`。**画面会有周期性顿挫**。
2. **阶段回绕那一帧**:`sub_6027D0` 的回绕分支里写死 `系数 = 1/6`,补丁没改。每个逻辑帧的第一帧又偏一次。

这两处很可能就是用户印象里「有点 Bug」的观感来源。**是否会真的导致联机不同步,静态分析给不出结论**(见 §5)。

## 2.5 ★第二份参考:HAOJUN0823 的 2009 版成品(2026-09-16 逐字节 diff)

来源 `G:\参考源码\红警3平台增强\red-alert-3-60fps-mod-main`(GitHub isma3iloiso)。**它和 §2 那份不是同一个补丁**:那份是 xinput 劫持 + 2012 构建,这份是直接给打好补丁的 `.game`,而且**基准构建与我们这份是同一次编译**(PE 时间戳 4A53BB67)。二进制里嵌着 `60FPS PATCH BY HAOJUN0823` —— repo 作者只是转包,所以 README 把改动写成「只改一个 4 字节值」是错的。

**真实改动**(`.data` 全节仅 2 字节不同):

| 位置 | 原版 | 补丁后 | 是什么 |
|---|---|---|---|
| `0xCAD5F4` | 15 | **60** | 原版只有 1 处引用的闲置全局,被拿来当「新渲染帧率」槽位 |
| `0xCAF9D0` | 15 | **30** | ★**逻辑帧率 = 模拟时钟** |
| `.text` 9 处 | 读 `0xCAF9D4` | 改读 `0xCAD5F4` | 让这几处看到 60 |
| `0x6C17CC` | fmul `[0xCDBC5C]` | fmul `[0xBC63D4]`(=0.03) | 粒子生成钉回原版速率 —— **和我们 P4 的做法、数值完全相同,独立印证** |

**三个缺陷:**

1. ★★★**动了模拟时钟**。`0xCAF9D0` 在 `.text` 有 279 处引用,全是秒→帧换算。射速量化函数 `sub_555670`:
   ```c
   if ( !this )  return a2 * dword_CAF9D0;                                    // 秒 × 15 = 帧
   if ( a3 )     return (int)ceil((double)(a2 * dword_CAF9D0) * this[111]);   // 向上取整
                 return (int)(float)((float)(a2 * dword_CAF9D0) * this[111]); // 向下取整
   ```
   把 15 改成 30,取整边界全部平移:

   | 单位 | 纸面 | 原版实际 | 补丁后 | |
   |---|---|---|---|---|
   | 水翼船 | 0.1s | 0.133s(2 帧) | 0.100s(3 帧) | 快 33% |
   | 海啸坦克 | 0.5s | 0.533s(8 帧,DPS 37.5) | 0.500s(15 帧,DPS 40) | 快 6.7% |
   | 射速本就是 1/15 整数倍者 | 0.2s | 0.2s | 0.2s | 不变 |

   ⇒ 与原版客户端**必然不同步**,而且**改了平衡**。用户 2026-09-16 联机实测「有些单位射速有问题」,现象与机制逐条吻合。社区实证见 B 站「射速研究报告」(小琪Kirit / 苯环,cv37453753):「1/15秒是RA3这款游戏录像文件的逻辑帧」,以及水翼 0.133、海啸 0.533/DPS37.5 等实测值 —— 与二进制推算完全一致。
2. 算 r 的代码本构建有 **5 处**,他只改了 2 处 ⇒ 他那份里 r 不一致(改过的 60/30=2,没改的 30/30=1)。
3. `sub_51A4D0` 的乒乓动画从 15/30 变 60/30,**快 4 倍**;`0x8F3CDC` 视觉步长仍是 1/30,渲染到 60 帧后**快一倍**(我们 P6 修掉了)。

**★他有一点比我们原设计好,已采纳** —— 见 §3。

## 3. 我们的设计(与参考补丁的区别)

0. ★★★**不写共享全局,只重定向读者**(2026-09-16 从 HAOJUN0823 那份学来,已落地)。
   客户端帧率全局 `0xCAF9D4` 在本构建有 **119 处读者**。原设计是「把它写成 60,再把不该变的逐个钉回去」——
   **默认全都变,漏掉一处就静默改错**。现在改成:那个全局**一个字节都不动**(仍是 30),只把确认需要新值的
   读者的操作数改指向我们自己的 `g_fpsRender` —— **默认全都不变,漏掉一处只是保持原版行为**。
   两者的失效方向相反,必须选后者。
   我们的重定向清单(11 处,离线检查器已逐处核对):

   | 组 | 处数 | 地址 | 说明 |
   |---|---|---|---|
   | R1 算 r | **5** | 5FFAD1 / 60283E / 616257 / 61B59C / 62935E | 判据:被除数=渲染帧率全局 **且** 除数=逻辑帧率全局。五处算出的 r 都存进同一个对象字段 `+92`,**必须全改**;★参考成品只改 2 处,导致它那份 r 不一致 |
   | R2 派生量 fild | 3 | BB30D8 / BB3108 / BB3138 | 三个「每帧时长」派生量函数 |
   | R3 某量÷帧率 | 1 | BB3C59 | |
   | R4 缓存进对象字段 | 1 | 53E90A | ⚠用途未独立确认(IDA 无伪代码),跟随参考实现 |
   | R5 时间换算 | 1 | 6297C9 | ⚠同上 |

   另有 4 处代码补丁(批次 / 插值系数 / 粒子生成常量 / 视觉步长)+ 3 处派生量**存量值**改写(引擎启动时就算好了,中途注入不会重算)。撤销表共 18 条。
   ⇒ 原 P5(粒子过期读帧率全局)**不再需要**:那个全局保持 30,它自然就是对的。
1. **不写死偏移**:全部用特征码扫描定位,并核对上下文;任何一处找不到 / 不唯一 ⇒ **整体不安装**。
2. **阶段调度自己算**:一个纯函数 `frameSchedule(r)` 给出「每个客户端帧该跑到第几个阶段」,保证
   - 每 r 个客户端帧正好跑满 6 个阶段(逻辑帧率恒等于原版);
   - 阶段序列单调不减、不跳号;
   - r = 2 时与原版逐帧一致(**回归判据:开补丁后 30 帧行为与原版逐值相同**)。
3. **插值系数三处一起改**:批次前(`sub_6027D0`)、批次后(`sub_616130`)、回绕分支,统一成 `本逻辑帧内已过帧数 ÷ r`,消除顿挫。
4. **粒子域**:参考补丁只钉了 2 处(10 处 `fmul [帧/毫秒]` 里的 1 处 + 1 处 `imul`)。我们先**逐处审计**这 11 个点,再决定钉哪些,并把结论写进本文。
5. **失败回滚**:任何一处写失败 ⇒ 全部还原;安装状态与每一处的原始字节都留在内存里,支持**运行时一键关闭**。
6. **可开关**:默认关;由外部命令开启(见 §6),方便 A/B 对比。

| 项 | 怎么验 | 为什么这么验 |
|---|---|---|
| 调度数学 | 离线单元测试(`tests\test_schedule.cpp`),枚举 r = 2/3/4/5/6,断言「每 r 帧满 6 阶段」「单调不跳号」「r=2 与原版逐帧相同」 | 不需要游戏,失败在写 DLL 之前就暴露 |

| 观感 | 开 / 关对比录屏;重点看单位移动是否有周期性顿挫(§2 的缺陷 1/2) | 顿挫正是参考补丁的病灶 |
| 联机 | **全部单机项通过之后**再谈;先两实例本机对局,一端开一端关 | 不拿别人的对局做实验 |

## 7. 「还能改什么」的初步评估(2026-09-16,证据在括号里)

| 想法 | 结论 | 依据 |
|---|---|---|
| **突破 2GB / 4GB 内存限制** | **有戏,而且 EA 自己做过**:2009 构建 PE 头 `LARGEADDRESSAWARE` = 关(2GB 上限);**2012 构建 = 开**。开这一位(改 PE 头 1 bit)即可在 64 位系统上拿到 ~4GB | 本轮实测两份 exe 的 PE 头 |
| 同上 · 风险 | 老引擎若有「指针当有符号整数」的地方,地址跨过 2GB 会崩;**只能实测**。另外这一位在**进程创建时**由内核读,运行时改内存无效 ⇒ 要么改文件(与联机指纹冲突),要么用平台启动时的独立副本 | 机制所限 |
| 显存 | 与「4GB」不是一回事:游戏是 32 位 D3D9,显存主要受地址空间与 D3D9 资源管理限制;先做 LAA 再看 | — |
| **多核 / CPU 吃满** | **不是有个开关锁着**。之前 LIVE 剖析已实测:sim 是单线程,**提优先级、绑核都无效**;卡顿 = 单线程计算量(密集单位的碰撞对 O(N²) → 逐单位避让范围查询 O(N·k) → 逐单位路径采样) | 记忆 `project-ra3-perf-pathfinding`(含采样剖析、LIVE 实验记录) |
| 同上 · 可行路线 | ① 已验证有效的杠杆:碰撞分组早退、避让查询跳过(LIVE 实测热点塌掉);② 治本方案 = 流场寻路 + 极简分离(注入点已全链定位);③ 真多线程化 sim = 需要改确定性核心,**不建议** | 同上 |
| **90 帧 / 120 帧** | ★**90 帧比 60 帧更简单**:引擎两逻辑帧之间固定 6 个插值阶段,`r = 渲染÷逻辑`。r=6(90 帧)是天然整数解 —— 每个客户端帧正好 1 个阶段,`sub_5FFAD0` 里本来就写着 `if (r >= 6) ... == 1` 这条分支,而且引擎自带的「阶段×0.16666667」在 r=6 时**本来就是均匀的**。⇒ 90 帧**只需要那 11 处重定向**,批次补丁和插值系数补丁都可以省掉。离线断言:`test_schedule` 两条 PASS(与原版公式逐帧相同 + 系数逐值相同) | 本轮 26 PASS |
| 同上 · 120 帧 | r=8 超出 6 个阶段,必须有「本帧不推进阶段」的帧(我们的调度给出 `1 2 2 3 4 5 5 6`)。但引擎逐帧那处(`sub_6027D0` 里 `this[22] = v4 + 1`)是**无条件 +1**,6 帧就凑满一个逻辑帧 ⇒ 逻辑会跑成 120/6 = **20Hz,比原版快 33%**。所以 120 帧除重定向外**还必须改 `sub_6027D0` 的逐帧推进**,让它按我们的调度决定这一帧推不推。DLL 现在对 r>6 直接拒装 | 离线断言 1 条 PASS |
| 其它二进制改造候选 | 单位数量上限、AI 上限、镜头拉远、分辨率 / UI 缩放、录像倍速 —— 都属同一类「找到常量 / 代码点再改」,可逐个立项 | 待评估 |
