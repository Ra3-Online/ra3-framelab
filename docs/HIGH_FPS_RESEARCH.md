### 日志证据和原生路径

对应日志 `framelab-20261027-22468.log` 为 highfps3、165 档、组 `0x1FFA8FFF`，SHA-256 `9da44cdd5804a54a322c6c6097a1ac4381965198ffec780d3d53310c79a45ef7`。12:37:13 已报告键盘 / 边缘步长从 100 改为 18.182，并明确写着“右键拖拽卷屏不在此列”。因此本次确属已有卷屏选项的覆盖缺口。该日志的炮塔读点 / 采集计数已命中，但计数本身不能证明所有车型或场景验收。

原生 `0xABFF40` 计算当前鼠标与按下锚点的 X / Y 偏移，在 `0xABFF9E` 附近读取当前两轴系数和用户右键速度，再由 `0xABFFB6` 的两条 MULSS 得出位移；随后提交给视图回调，保留方向反馈、碰界和锚点处理。右键状态的原生虚函数指针位于 `0xC80F94`。旧代码没有对这一路的每次更新位移归一，因此在更高更新次数下累积过快。

复核此前已保存的 [SAGE-Unlocked a770379 的 Unlocker.cs](https://github.com/TheeHorse/SAGE-Unlocked/blob/a770379e35bf814ae9a0954f192b96b60b800b33/src/Unlocker.cs)，其中 `FindTurretInterp` / `PatchTurretInterp` 专门处理炮塔：原生代码维护前后角度，插值等于 1 或与上次相同时会切换端点。上游在原生批次模式以阶段 6 识别完整周期完成，给炮塔独立进度。本次在线读取该固定源码页失败，引用依据为此前保存的同一提交源码，没有宣称核对了最新主分支。

### 为什么移动修好而炮塔仍粗糙

单位整体位置 / 朝向与炮塔骨骼属于不同路径。候选 2 只修改 `0x52F5FF` 的单位变换读点；炮塔函数 `0x8FB650` 在 `0x8FB6D2` 另读 engine+0x60。它用两个缓存角度插值，并在以下情况重新采集：`alpha == 1 || alpha == lastAlpha`。后者在原版少量客户端更新下用于刷新缓存，高帧下连续多次相同的 0.5 / 1.0，或暂停 / 等待时插值停住，会反复采集并使两个端点合并，画面转为阶梯。

因此，这一轮同时分离炮塔的显示进度和端点提交条件。单独替换浮点读点不能可靠处理相同进度与重复绘制。

### 具体实现与写入范围

`FlHighTurretClock` 只观察原高帧调度的成功批次。阶段 6 成功结束时递增显示缓存代号、记下完成时间；中间帧从 0 平滑增加到小于 1 的上限 0.9999。它不安排或执行模拟阶段，不修改逻辑时间、瞄准角、武器状态或随机数。原位置插值保持候选 2 的实现。

| 新站点 | 原生 VA | 写入字节 | 作用 |
| --- | --- | ---: | --- |
| 炮塔显示进度 | `0x8FB6D2` | 5 | 独立读取炮塔进度；保留前面 TEST EBP 的标志，供后面 JE 使用 |
| 水平角缓存条件 | `0x8FB7BD` | 19 | 当前缓存未提交过本代号时，才走原生角度采集分支 |
| 俯仰角缓存条件 | `0x8FB91C` | 23 | 同一提交判据；保留原俯仰角处理，并未另外发明俯仰动画 |
| 缓存标记写回 | `0x8FBCAA` | 5 | 原五浮点缓存最后一个 lastAlpha 字段改存原始 32 位代号 |

四处作为必需集合加入安装事务，高帧总数由 8 变为 12。完整签名、引擎读取 / TEST 前缀、两个原生跳转目标及后续指令均有静态合同；缺失、重复或漂移拒装。预映像、写后和故障回滚覆盖四处新站点。30 / 60 / 90 不安装这组补丁。

缓存仍由原函数的 `0x8FB5A0` 原生容器持有，位置相同，大小不变。本次只把最后一字从浮点“上次进度”改作本路径的代号；前四个角度值仍由原生采集指令写入，原生初始化哨兵及 ±π 最短转角计算保留。水平和俯仰共用同一次提交判据，最后才写标记。无需保留可能失效的对象指针或自有缓存表；重复绘制同一缓存不会再次提交，等待和插值封顶也不会伪造新端点。全新缓存及重新出现的缓存保留原生初始化 / 限定提交流程。

该显示缓存的含义变化只适用于已安装的高帧代码。切换版本仍须退出游戏后重新启动，不能把热卸载当作可靠流程。像此前候选一样，本轮字节恢复测试不构成运行中卸载业务安全的证明。

## highfps1 历史研究与构建记录

日期：2026-10-26。源码版本：`0.2.4-dev1-highfps1`，GUI 标题“高帧候选 1”。研发起点为 `cf7e90782cab2ea239826407c33b03c9d5371502` 的 visual6。

SAGE 在 `PatchScheduler` 中使用接近原版实际节拍的 66 ms 逻辑周期，而不是直接按理想 66.666… ms 强行推进。原因是该零售限帧路径使用 33 ms 的客户端半周期。此处“逻辑 15 Hz”是游戏的名义基准；墙钟测量可能约 15.15 Hz，也可能受场景和网络等待压低。原版对照及匹配状态比单看一个 Hz 数值更有意义。

本轮为 FrameLab 编写对应 C++ 调度器与 x86 适配层，参考上述设计，没有复制上游 C# 补丁生成器或它生成的机器码实现。来源记录同时列入 [NOTICE](../NOTICE.md)。

## 2. 为什么旧实现卡在 90

旧路径用 `r = 目标 FPS / 15` 把一次逻辑周期的六个阶段分配给显示更新。90 时 `r=6`，已经每次只推进一个阶段；把 r 简单增加到 8 或 16，既不能正确表达“此帧零阶段”，也不能保证等待中的模型条件、变换冲刷和销毁队列不会被重复消费。

新候选保留旧路径用于 30 / 60 / 90；120 以上采用以下顺序：

1. 引擎更新入口恢复上次原生批次产生的模拟插值值，然后才运行原有的更新前处理。
2. 三处模拟边界门分别消费一次性令牌；重复绘制不会因为阶段一直停在 3 或 6 就反复放行。
3. 用 `QueryPerformanceCounter` 判断下一半周期是否到期。未到期时绕过阶段推进，执行原生绘制出口。
4. 到期时让原生调度器完整执行 1、2、3 或 4、5、6；内部阶段顺序、网络判断、原生模拟插值写入和调用结构保留。
5. 批次正常结束后保存原生模拟插值，再计算本帧独立显示插值。新 tick 只在成功完成第一半批次时发出一次。

状态机在 [high_fps_schedule.h](../src/high_fps_schedule.h)，运行时适配和七处补丁事务在 [high_fps_runtime.inl](../src/high_fps_runtime.inl)。墙钟只决定什么时候尝试原生批次，不用于生成逻辑随机数、选择对象、改变逻辑时间步长或跳过游戏阶段。

### 网络等待、暂停和插值

原生网络检查拒绝新的 tick 后，阶段会回到越界等待状态。候选观察这一结果，保留待执行批次，不给该次尝试记成功，不发新 tick，也不凭墙钟自行绕过网络检查。网络放行后从原生第一阶段重新进入。

每个显示更新最多执行一个原生半批次。长时间暂停、时钟倒退或积压超过四个半周期时，重新定位墙钟期限；丢弃的是墙钟欠账，不是游戏阶段。这样避免恢复后在一帧里密集追赶大量逻辑。实际更新低于约 30 次/秒时仍会受吞吐限制，不能把这一设计理解为任意低帧都能维持游戏速度。

显示 alpha 在已完成第一批时限制于 0–0.5，第二批之后限制于 0.5–1；使用已过时间及最近显示间隔估计本帧位置。下一更新入口先恢复保存的原生值，防止不一致的渲染时间直接流入更新前的模拟工作。是否还有其他显示路径的副作用进入同步状态，需要实机 CRC 验证。

### 五处倍率读者必须分工

所支持镜像有五处相同形式的整数除法，两个操作数分别指向客户端和逻辑帧率全局。旧路径统一指向显示倍率；新路径按实际用途分开：

| 原生地址 | 新路径的处理 |
| --- | --- |
| `0x5FFAD0` | 整个相位判定入口由“本显示更新是否刚成功开始新 tick”替代 |
| `0x616256` | 调度器继续使用原版 30 / 15，即两批次 |
| `0x60283D`、`0x61B59B`、`0x62935D` | 保留目标显示 FPS / 15，供引擎 `+0x5C` 显示预算使用 |

`0x629745` 的原生限帧器会消费 `+0x5C`。因此不能把全部倍率读者都改成 30。高帧安装要求完整且唯一的上述五处；缺少、出现未知位置或除数不符都拒绝安装。测试直接调用真实的解析函数验证这项分工。

### 毫秒限帧误差

120 FPS 的单帧预算是 8.333… ms；240 是 4.166… ms。原生整数截断会分别变成 8 和 4 ms。候选保留原限帧器的网络缩放和浮点控制字，只累积被截掉的小数并在后续帧补回。测试实际执行编译后的 x87 跳转桩，核对预算总和及浮点栈深度；它不是实际 Present 测量。

## 4. 围墙、光团与高帧显示

回归检查发现，visual6 的围墙首显和 GPU 光团包装内部原先只接受 60 / 90。只增加 GUI 档位会使高帧调用直接跳过这些修复；本轮将其限定目标扩展到已接受的高帧范围，保留原墙件 / 光团模板和原生对象检查。

60 / 90 的光团可见寿命仍是 15.75 或 1.75，保持既有候选行为。高于 90 时，替换前最后一个显示样本更靠近池寿命终点，改为 `池寿命 - 15/FPS`；池寿命仍为 16 或 2，只改匹配模板的五个 GPU 顶点寿命，不偏移出生时间，也不增加发射或随机数消费。

CPU 时钟模型在所有高帧步长、多个发射相位及起点 0、约 100 秒、一小时上没有发现所测交接空隙或重叠。**八小时量级浮点时间戳仍存在反例**：部分档位出现模型预测空隙或重叠，测试保留并报告它们。没有 GPU 捕获或实机画面，不能据此宣布帝国 / 苏联光效在高帧已经修好。低于目标帧率运行时，部分既有特效时钟仍按显示次数归一，可能慢于墙钟；本轮没有把所有显示时间源改成墙钟。

回放快进、特殊速度、不同运行构建、长时间掉帧、切换场景时的视觉连续性均未做实机验收。高帧实验不覆盖旧 visual6 未验收的帝国灯光，也不继承其联机结果。

## 6. 使用候选及下一轮实机验收

GUI 提供 30、60、90、120、165、180、240；默认 120。DLL / CLI 接受 120–240 的 15 倍数。175 Hz 屏幕可先测 120，再测 165；240 目标可用于吞吐研究，但该屏幕不能每秒完整展示 240 个独立刷新画面。垂直同步会影响实际呈现率，判断时同时记录它、显示模式和 Present。

为保留已有产物，建议显式使用独立构建目录：

```powershell
.\tools\build.ps1 -Target all -BuildDir build\highfps-candidate1 -RunTests
.\tools\package-release.ps1 -Version 0.2.4-dev1-highfps1 -BuildDir build\highfps-candidate1
```

普通构建与测试不需要游戏；可选 `FLAB_IMAGE` 只读取使用者自行提供的游戏镜像。高帧程序需要用户另外手动打开这个新目录中的 GUI，版本为 `0.2.4-dev1-highfps1`，标题含“高帧候选 1”。已打开的旧 GUI 不会因磁盘上有新 DLL 而自动换载荷。

本轮用户要求只离线研究。等游戏空闲且用户授权实机测试后，按以下顺序推进：

1. 原生 30 正控与候选 120：核对安装状态、真实 Present、逻辑步进、场景速度、载具和各阵营建造 / 光团；先确认确实突破 90。
2. 双开 30 / 120、90 / 120，再补 60 / 120。沿用 Pool Party、两端原生观战、四个互相敌对凶残 AI、50000 资金。高帧端不得改变模拟参数来追求计数。
3. 相同条件再验证 165 与 240，以及必要的三端组合。用户此前接受约一小时观察；实际时长、正常胜负、崩溃或监控缺口分别记录。
4. 自然 CRC 按完整 metadata 键配对，并核对标量、重复次数、缺失、采集时效和有界原始状态。单看逻辑 Hz 相同或没有弹出错误框不算通过。
5. 帧数下降、网络等待、暂停恢复、正常结束和反复开局单独补测。正常败北、主动退出、访问冲突及读取器失败必须根据日志区分。

旧 visual6 在 Pool Party 的 90 / 30 观察约 58 分 16 秒，883 个共同完整自然 CRC 键一致，最终 90 端访问冲突退出。这是旧工件的有限证据，**不覆盖本候选，更不能写成 120 / 240 已经联机安全**。
