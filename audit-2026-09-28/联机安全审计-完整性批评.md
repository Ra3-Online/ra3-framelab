# 完整性批评：RA3 FrameLab 联机安全综合结论

本轮做了约 55 次纯静态调用（只读 dump 和二进制），没有写入任何文件。

## 一、本轮新证据：推翻或修正综合结论的地方

**1. 普通同步 CRC 不包含 Object 变换，也不包含模块 xfer**（置信度：很可能）

- **证据链：**
  - `sub_4F1D80` 的非 deepCRC 分支执行 `byte_CE2F5C=1`，然后调 `sub_4D7F40`（dump ≈208219/208221）。
  - `sub_4D7F40` 中 `v5=byte_CE2F5C; if(v5) v35|=8u`（184110–184118）。
  - `XferCRC::xferSnapshot`（0x985A00）调用 snapshot 的 vt+0xC。Object+96 处 snapshot 的 vtable 是 0xC4DB50（构造函数 `sub_7C1C90`，dump 805008），其 slot3 = 0x78F460，这个函数 Hex-Rays 没有反编译。
  - 0x0078F528–0x0078F531：`mov edx,[esi+4]; shr edx,3; test dl,1; jne 0x78F5F3`。这一段跳过了 12 个 float 的变换（obj+8..+0x34 → `sub_54A960`）。
  - 0x0078F6A4–0x0078F6AC：flag8 置位时走精简路径 0x78F6B2–0x78F85F，然后 `ret`。精简路径只包含：
    - `[obj+0x33C] vt+0x3C` 返回的浮点；
    - obj+0xE4、obj+0xE8；
    - `*(obj+0x450)` 在 +0x14..+0x1C 处的一个 Coord3D；
    - 一个 6 次的循环。
  - 完整 xfer（含模块）从 0x78F862 开始，只有 flag8 为 0 时才走。
- **对 R-1 的影响：** 原文写「取决于 CRC 是否包含变换（ZH 包含）」，现在应改为：DG-1 的 z 分歧只有传播到被 CRC 的量（血量、shroud、上面那个 Coord3D）时才会被检测到。DG-1 ↔ 源 II 的对应因此更弱。
- **对 R-3 的影响：** 0.01 阈值那一类效应能进 CRC 的通道只剩 shroud。
- **对 PSYS 的影响：** 结论不变，但理由应换成「CRC 精简路径不含模块」。

**2. 对象 CRC 是抽样的**（置信度：已确认）

- `byte_CAFF6C` 在 .data 中初值为 01，全镜像只有 3 处读（0x4D7FDE、0x4D82A7、0x4F847D），没有写。
- `sub_4D7F40` 每次只取每第 10 个对象（184124–184133），起点 GL+788 每次按 (+1)%10 轮转（184227）。
- 每 interval/10 帧就会发一次 545（`sub_4F81F0` 212800–212835 中 v12=1 的分支）。
- **影响有三点：**
  - (a) 实测到的 desync 帧只是检测帧，真正的分歧可能早得多。
  - (b) M1(b) 中「phase 6 销毁的对象多留一帧」会让 10 步抽样的相位整体移动。只要恰好碰上 CRC 帧，结果几乎必然不同，所以 M1 作为源 I 的解释力更强了（推测）。
  - (c) DG-1 的瞬时分歧即便能进 CRC，每次也只有大约 1/10 的概率被采到。

**3. 第 4 步的 deepCRC 方案本身会触发不同步**（置信度：很可能）

- deepCRC 分支不置 CE2F5C，于是 flag8 为 0，走的是含变换和模块的完整 xfer。非联机时 interval=1（212806–212812）。
- 因此回放时本地算出的 CRC 必然与录像里的 545 不相等。
- 要么先查清 545 不匹配时回放怎么处理，要么只比对两次本地 dump，不依赖回放判定。

**4. R-6 中的 `sub_6FDC60` 不是纯客户端：它是 ModelCondition 的延迟同步，会改变逻辑侧骨骼查询**（置信度：很可能，影响程度推测）

- **机制：**
  - `sub_6FB510`（646301–646314，362 个调用点）把 Object 挂进 CE5898 表。
  - `sub_6FDC60` 在每个客户端帧排空这张表，调用 `sub_52F360(obj+244, obj+160,1,0)`，执行 `qmemcpy(Drawable+612, …, 0x3C)`。
  - 逻辑侧骨骼查询 `sub_51E180`（248247）以 `this+153`（即 Drawable+612）为键。它有 20 多个模块区调用者：`sub_6D6CE0`、`sub_6DDE20`、`sub_6E44C0`、`sub_6EDFA0`、`sub_7047A0`、`sub_717B10`、`sub_71CAD0`、`sub_725D90`、`sub_73CF60`、`sub_74C0A0`、`sub_7623B0` …
- **后果：** 同步发生在客户端帧开头。原版只在 phase 3/6 之后同步，r=4 变成在 2/3/5/6 之后，r=6 每个 phase 之后都同步。CH-4 说「按 model-condition 键控，所以是确定的」，这只在原版边界下成立。
- 这是**源 I 的新候选**（例如发射骨骼决定投射物起点），可以套用 R-3 的门 `ph==3||ph>=6`。

**5. 排除：回放命令注入与 r 无关**（置信度：已确认）

- TheRecorder = CE2FD0，vtable 为 off_C10544，vt+20 = `sub_625CE0`（find_vt 找到 0xC10558）。
- `sub_625CE0` 在 this[9]==1 时调用 `sub_624670`（先剔除本地命令，再读当帧命令）。它唯一的调用点在 `sub_4F81F0` 的 phase 1（212895）。
- 附带结论：§1.1 的「+9==1 = 回放」从推测升为已确认。

**6. R-2 前提补强（仍然没有对抗复核）**

- engine（dword_CE2F8C）+0x180 只有两个写者：phase 5（213098）和 `sub_61B560`（455644）。
- `sub_4E2F60` 的其他调用者是 `sub_4F1A00`（全部清空）、`sub_4EE230`、`sub_4EE880`，都不是逐帧调用（后两者属推测）。
- 所以 wrapper 只在 `ph>=6` 时放行，是与原版一致的。

**7. R-6 中可以剔除的项**

| 调用 | 结论 | 依据 / 置信度 |
|---|---|---|
| `CD6C9C vt+156` | 调试帧标记，很可能无害 | CD6C9C 是 Debug 单例（19265 `?PreStaticInit@Debug@@`） |
| `sub_99F970` | 客户端 | QPC 计时 + D07A90 线程同步 |
| `sub_62B190` | 只返回 CE3A30 | 它调用的 `sub_6783D0` 未审 |
| `sub_5FD6D0` | 很可能是 UI | 读选中 / 鼠标下的 drawable（CDB73C），推测 |

**8. 排除：StructureUnpackUpdate `sub_6F6CB0`**（置信度：已确认）

- a3=0 时用显示帧号，唯一调用者 `sub_6FD550` 传的就是 0。
- `sub_6FD550` 的调用者都在客户端或 UI：256671、`sub_70F350`、1094868、1449xxx。

## 二、仍然薄弱的结论

- **R-5 修法的作用面没审。** `sub_5FFAD0` 有 4 个调用者：
  - `sub_542DF0`：Ghost，已审；
  - `sub_70F350`（663116）：插值，`if(!mid) this+96 -= this+32`；
  - `sub_6293D0`（466731）：节拍，`goto LABEL_41`；
  - `sub_602720`（433868）：联机跳过渲染。
  - 60 帧下这个测试现在恒为假，另外三处的现有行为可能已经被视觉修复所依赖。把 0x5FFAD0 整体移出 R1 会同时改变它们，建议只改 `sub_542DF0` 的调用点，或者逐个审。
- **源 II 的实测区分度很低。**
  - HANDOFF 1150–1152 里三条源 II 臂（0x2CFFE / 0x2CFE0 / 0x2CE00）都同时开着 0x200 / 0x400 / 0x800 / 0x4000 / 0x8000 / 0x20000，这些位从未单独关过。源 I 臂在约 2400 帧先出事，会把源 II 掩盖掉。
  - 所以 DG-1 与源 II 只是「相容」。CLOCK（r=2 时时钟每逻辑帧只走 33 ms）、ANIMSTEP、ANIMPROBE 同样没有被排除。
  - 18.6b 表中「帧率真提到 60?」那一列，如果来自已作废的 mask_fps_probe，那么源 II 臂的真实渲染率是未知的。这更偏向「依赖目标值」的机制，而不是「依赖渲染次数」的机制。
  - 第 1 步应当增加两条臂：`0x28FFE` 去掉 0x8000、`0x28FFE` 去掉 0x20000。
- **R-4 漏了第二个冻结触发。** `sub_5571F0(CDD190)`（297533，脚本引擎 this[99054] / this[99049]）与镜头无关，而 `sub_56F220` 在每次 phase 1 尝试时都会跑。很可能只在脚本调试器模式下出现（推测）。
- **P6 / P6b / CLOCK 的「安全」只沿直接调用查过。** 反方向——逻辑代码调用绘制 vtable 取动画完成或进度（`sub_8EDED0` 家族，vtables 0xC62B30 / 0xC62BB0 / 0xC62D4C / 0xC62ECC / 0xC63064）——没查。
- **DG-1 的触发单位仍未定**（template+96 有两种解读）。在第一条之后，还需要重新论证它能否被检测到。

## 三、调查者之间的矛盾

- **phase-scheduler 说「SP 和回放都有 QPC 门」。** 实际只有回放有：`sub_616130` 只在 `CE2FD0+9==1` 时调用 `sub_615BF0`（451077–451081）；单机实时只看 `GL+348==0`（451044）。
- **vanilla-premise 说「CRC 覆盖逻辑对象列表」。** 实际是按 1/10 抽样，而且只取精简字段（见一.1、一.2）。
- **CH-4 说「骨骼查询确定」。** 实际键控的是 Drawable 上的延迟副本（见一.4）。
- **caf9d4 说「DERIVED2 关不掉」。** framelab.cpp:457 写明「从默认里去掉即可回退」。它可以关，只是从来没测过。

## 四、没有覆盖的维度

- **暂停落在组内。** r=4 时，phase 1 执行的暂停命令会让游戏停在 entry=2，而原版只会停在 3 或 6。暂停期间 `sub_626620` 仍然每帧跑，`sub_6FDC60` 不受任何门约束。test_schedule 要覆盖这种情况。
- **GL+167 未审。** `sub_616130` 在 451053 处 `if(GL+167) goto LABEL_18`，会绕过联机网络门。它的语义没查，在 r>2 下的行为也没查。
- **读档和开局初值。** loco+0x58 是否参与 xfer、`sub_61B560` / `sub_627A20` 设置的 this[22] 初值，都没查。
- **官方数据（非 Remix）。** DynamicsUpdate 和两栖 locomotor 的使用情况没查，上次 grep 超时。
- **CAFF6C 在 0x4D82A7 的第二处读。** 其他子系统是否也按这种方式抽样，没查。
- **联机节拍。** Network::update（CE3A8C vt+20）按 phase 1 尝试次数调用，90 帧下频率会变。它对 run-ahead 和 `flt_CAFF7C` 递减（`sub_602720`）的影响，决定了 30 对 90 能否同场不超时。
