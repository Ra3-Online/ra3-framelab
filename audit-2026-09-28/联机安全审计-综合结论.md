## 0. 一页结论

1. **原版的 r 固定为 2，这一点在代码层面已确认。** HANDOFF §22.3 说「原版本来就允许两台机器渲染帧率不同」，这句话只在一个意义上成立：各机 GameClient::update / 绘制的次数可以不同。原版机器之间从来没有出现过 r 不同，也没有出现过每逻辑帧的显示帧号增量不同。凡是「按客户端帧做、又碰到模拟」的代码，在原版里都是确定的，到 r=4/6 才会分叉。
2. **已确认 / 很可能的模拟侧风险有三类：**
   - **①** 与 FL_G_RATIO 无关：**DG-1**，载具/步兵的高度过渡斜坡长度 = 本机 `flt_CDBC50 × 0.5`。两个独立维度都查到了它，复核 6/6 成立。
   - **②** 只在 r>2 时出现：**客户端帧开头的延迟模拟工作随 r 换位置**，包括 processDestroyList（M1）和变换变更冲刷（M2）。
   - **③** 只在脚本时间冻结时出现：冻结重试期间原版每帧补跑 phase 2+3，而补丁在 r=4 只补跑 phase 2，r=6 一个都不补跑。
3. **修复能达到的程度：**
   - ① 能修到逐位回到原版。
   - ② 用「原版边界门」可以按构造回到原版的相对顺序，前提是 `sub_626620` 里其余逐客户端帧的工作都清点过（目前还没清点完）。
   - ③ 在 FL_G_CAMERA **关**的情况下能精确回到原版，开的情况下只能近似。原版联机很可能根本不走这条路（推测）。
4. **静态分析证明不了「清单完整」。** 能否同场只能靠回放臂与 deepCRC 对账来证伪或确认。
5. **源 I / 源 II 的对应关系全是推测：** DG-1 ↔ 源 II（约 10800 帧，与 RATIO 无关），M1/M2 ↔ 源 I（约 2400 帧，只在 RATIO 开时出现）。下文第 5 节给出能一次区分它们的回放臂。

## 1. 联机安全结论

### 1.1 关于「原版固定 r=2」这个前提

| 结论 | 证据 | 置信度 / 复核 |
|---|---|---|
| r 只由两个从不被写入的全局算出，即 `dword_CAF9D4 / dword_CAF9D0` = 30/15 = 2，每台原版机器都一样 | 5 处 R1：0x5FFAD0、0x60283D、0x616256、0x61B59B、0x62935D；其余 `div [CAF9D0]` 的被除数都不同；119 处 CAF9D4 引用全部是读 | 已确认（phase-scheduler F5/F6、caf9d4 F2、vanilla F1 三路互相独立一致；本身无单独复核） |
| 每个逻辑帧 = 2 个客户端帧：[1,2,3] 与 [4,5,6]。任何路径都不会在一个客户端帧里跑超过一个逻辑帧 | `sub_616130` 的批次循环在 451094–451104（本轮补读），其中 `if (r<6)` 的 target 为 `6*((r*(a2-1))/6+1)/r`；主循环 `sub_6293D0` 每轮只调一次 update | 已确认 |
| 慢机或网络卡顿时插入的是「空转帧」（phase 1 的门失败时 `CDB750+196=0`，`this[22]` 恢复为 7、8、…），r 不变。空转帧不推进显示帧号，延迟工作也被各自的闸（GL+796、engine+384、显示帧去重）挡住，所以对模拟无影响 | `sub_6027D0`：失败时执行 `this[22]=v8`（本轮补读 433950–433960）；`sub_626620` 只在 +196 置位时 `setFrame(getFrame()+1)`（464724–464733） | 很可能（phase-scheduler ruled_out） |
| 原版各机之间真正会不同的是 GameClient::update / 绘制的次数：当 `this[95]<=1`（有滞回：≤17 fps 降为 1，到 30 fps 才回到 2）或网络追帧时，`sub_602720` 会跳过更新 | `sub_602720`（433856–433884）、`sub_6293D0`（466807–466828） | 已确认（复核中大家都同意这一部分） |
| 显示帧号 CDB750+0x48 在每台原版机器上每逻辑帧恰好 +2；打了补丁后变为 +r | 自增发生在跳过测试之前（464728–464733），`setFrame` 在全镜像中只有这一个调用者 | 已确认（vanilla F2 复核中唯一成立的一半） |
| **原版里「时钟在各机锁步一致」这一说法是错的** | 在跳过的机器上，phase 1–3 读到的 CE1388 落后 33 ms，只有在 phase 4–6 读、或按整个逻辑帧合计时才一致。另外，`sub_626620` 在跳过测试之前做的那些工作，其执行次数在原版里本来就随空转次数变化 | 已确认（vanilla F2 复核 1/3，被证伪的部分） |
| 联机没有任何帧率协商。run-ahead 只由发送方本地决定；MSG_ANNOUNCE_RTT 只写网络表 | `sub_606B70` 消息表（ids 501–595）、`sub_66F730`、`sub_62BE40`、`sub_644E80` | 很可能（无复核） |

**结论：** 原版能容忍的是各机的渲染次数和空转次数不同，**从来没有容忍过 r 不同**。所以真正的要求是：模拟状态必须与 r、与显示帧号的节奏、与补丁改写过的派生值全部无关。

**本轮补读的补充：** `sub_616130` 中 phase 1 的 QPC 计时门（`sub_615BF0`）只在 `dword_CE2FD0+9 == 1` 时生效（451063–451069）。`sub_626620` 在 `+9==1` 时会调回放观战镜头 `sub_620900`，因此 +9==1 应当就是「回放播放」模式，这是推测。换句话说，**单机实时对局里 phase 1 没有计时门**，逻辑速率只靠限帧器维持（推测）。§18 的全部 determinism 臂都是回放，所以都受这个计时门约束。

### 1.2 模拟侧风险（按严重度排列）

#### R-1（最严重，与 RATIO 无关）：运动器（locomotor）切换后的高度过渡斜坡，长度取本机帧率。对应 derived-globals DG-1（复核 3/3）与 caf9d4 F1（复核 3/3）。

- **机制：**
  - 单位切换运动器时，`sub_73ABC0` 把倒计时初值写为 `flt_CDBC50 × 0.5`。
  - 消费端 `sub_715ED0` 和 `sub_778AA0` 按 `(start−preferred)/(flt_CDBC50×0.5)×cnt` 计算高度偏移，每次运动器更新 `cnt -= 1`。
  - 这个更新是**逻辑帧节奏**：调用链为 AIUpdate::update `sub_7DCFD0` → `sub_73ABC0`，以及 `sub_7D8120`（维持当前位置）/ `sub_7D7BA0` / `sub_7DB200` → `sub_78D510`。
  - 算出的 z 写进 Object 变换，路径为 `sub_7D7BA0 → sub_7C1300 → sub_7E35D0`，或在 0x007D83B5 / 0x007D83C7 经 `sub_7ADF20`。同时写入待定位置 Object+552..560 / +566，由 `sub_6FD340` 用来估算速度。
  - FL_G_DER_FPS（0x200，属于默认的 DERIVED2）把 `flt_CDBC50` 的存量值改写为目标帧率，结果：
    - 原版：15 逻辑帧 = 1.0 s（**不是** HANDOFF §22.4 写的 0.5 s）
    - 60 帧：30 逻辑帧
    - 90 帧：45 逻辑帧
  - 同一逻辑帧上，不同帧率的机器算出的 z 不同。
- **证据：**
  - dump 699169：`*(float*)(v7+88) = flt_CDBC50*0.5;`
  - dump 668216：`v11 = (v10/(flt_CDBC50*0.5))*v9; *(this+88)=v9-1.0`
  - dump 748994（在 `sub_778AA0` 内）
  - 指令：
    - `0x0073AC7C F3 0F 10 05 50 BC CD 00`
    - `0x00715FD9 F3 0F 10 25 50 BC CD 00`
    - `0x00778B4B F3 0F 10 1D 50 BC CD 00`（三份复核都核对过这些字节）
- **触发条件与范围：**
  - 只在新旧运动器的「偏移 + PreferredHeight」不相等时才触发，而且只有 `AIUpdate::update`（0x7DD065）这一处会启动斜坡。0x7A983E 调用前会先把 +540 清零，所以不会启动。
  - 分歧是暂时的：斜坡结束后 z 精确收敛。它是否会被发现，取决于 RA3 的 Object CRC 是否包含变换。祖先 ZH 包含，RA3 未证实。
  - **复核者之间的分歧：** 关于 locomotor template+96 的枚举含义，一位读作 BehaviorZ（0 = 地面，1 = SEA_LEVEL，并列出了 10 个 PreferredHeight 非零的水面运动器，例如 HumanWater −1），另一位读作 Appearance（0 = TWO_LEGS，1 = FOUR_WHEELS，并举例 Tanya 陆 0.1 / 水 −1）。**哪些单位会触发目前未定。** 两位都认为游泳步兵或两栖单位下水、上岸时会触发，这仍是推测。
- **修法：**
  - 把三条指令的 disp32（地址分别在 **0x0073AC80 / 0x00715FDD / 0x00778B4F**）从 `0x00CDBC50` 改指到补丁自有的只读 `static const float g_simFps30 = 30.0f`。
  - 三处全部命中才安装，否则一处都不改。
  - **不要**碰 0xBE6678 处的 0.5，它是共享常量。
  - 新建一个独立的开关位。现在 FL_G_EVERYTHING = 0x1FFFFFFF 已经满了，新位需要同步放宽它和 GUI 掩码。
  - 这个问题**只能**这样修，或者改为「停止改写存量值、只把客户端读者改指到 g_fpsRender」。后一种做法要先给 `sub_6D7520`、`sub_6DCAE0`、`sub_783360` 定性（见 R-8），现在不宜采用。
- **修后能否逐位确定：** 这三处会逐位回到原版（同一条 movss、同一个 30.0f）。能否据此说整个 `flt_CDBC50` 通道都干净，前提是它没有别的模拟读者：17 条引用已经全部分类，剩下 DG-2 和 3 个未经复核的归类。
- **同配置玩家（都装补丁、目标帧率相同）：** 双方的值逐位相同，所以 DG-1 **不会**让同配置的两台机器互相分歧，只会让它们都偏离原版。这是推理。

#### R-2（高，r=4/6）：processDestroyList（M1）被挪到 phase 6 **之前**执行。对应 phase-scheduler F1，**这一条本身无复核**，但 PS-2 的 3 位复核者都把它列为「最强的模拟可见项」。

- **机制：**
  - phase 5 在 0x004F8998 执行 `mov byte [ecx+0x180],1`，请求删除。
  - 这个请求只由 `sub_619BD0` 在下一个客户端帧开头消费（调用点 0x006266FE），内容是 `sub_5F4790` + `sub_771BF0` + `sub_4E2F60`。`sub_4E2F60` 会把对象的模块从睡眠桶 GL+220 中 swap-remove 掉，把对象从 GL+180 链表摘下并删除。
  - 原版 [4,5,6] 在同一帧，所以删除总是发生在 phase 6 之后、phase 1 之前。r=4 与 r=6 都会让删除发生在 phase 5 与 phase 6 之间，带来两个后果：
    - (a) phase 6（桶 3）遍历的是已经 swap-remove 过的桶，存活模块的更新顺序与原版不同。
    - (b) phase 6 里被销毁的对象要一直留到下个逻辑帧 phase 5 之后才被删，因此会经过 phase 1 的 CRC 点（`sub_4F1D80 → sub_4D7F40` 遍历 GL+180）和 `sub_78E560` 的尾部遍历。CRC 是否跳过「已销毁、未删除」的对象是推测。
- **证据：**
  - dump 213092–213100（phase 5 置位）
  - 454035–454041（`sub_619BD0` 读取并清除）
  - 194189–194269（`sub_4E2F60`）
  - 184128–184139（CRC 遍历对象）
  - schedule.h：r=4 时 phases_done = 2,3,5,6
- **修法（本轮补读修正了原提案）：**
  - 原提案是「跳过 call」。但 `sub_619BD0` 在 +384 分支之外还有别的工作：`sub_9B6430`，以及 +384 分支内部的 `CDB750 vt+128`、`sub_6197F0`（454043–454050）。所以**不能跳过整个 call**。
  - 做法：把 0x006266FE 的 call 改指到 wrapper。wrapper 读 `ph = *(int*)(engine+0x58)`，其中 engine 就是这里的 ecx（TheGameEngine）：
    - 若 `ph >= 6`，原样调用。
    - 否则先 `saved = byte[engine+0x180]; byte[engine+0x180]=0;`，调用原函数，然后 `byte[engine+0x180] |= saved`。
  - 这样删除只会在「上一个完成的 phase ≥ 6」的帧开头发生，与原版一致（原版消费时入口值恒为 6）。
  - `sub_61B560`（新局）自己会置 +384 并直接调用 `sub_619BD0`，不经过 0x6266FE，不受这个修法影响。
- **修后能否逐位确定：** 删除点相对各 phase 的位置按构造与原版相同。

#### R-3（中高，r=4/6）：对象变换变更的延迟冲刷（M2）换位。对应 phase-scheduler F2（复核 2/2）。

- **机制：**
  - `sub_7ADF20` 把第一次移动前的旧变换快照下来，并把对象挂进双缓冲表 `dword_CE5930[CE5870]`。
  - `sub_4D5600`（在 `sub_626620` 的 0x006266F7）于 GL+796==0 时调用 `sub_7C2670` → `sub_79E800(…,2)`。GL+796 在每个 phase 入口都会被清零（212756）。
  - `sub_79E800` 的模式 2 会：
    - 调对象 vt+24（`sub_716C60`：给 shroud、+0x4E8、PartitionManager 打脏标记）；
    - 调 +0x328 / +0x32C 模块的 vt+20（很可能是容器让乘员跟随移动，推测）；
    - 置 DynamicsUpdate 的 +0x39；
    - 清除 +244→+319 的 bit 1–2。
  - 冲刷位置：原版在 phase 1、4 之前；r=4 在 1、3、4、6 之前；r=6 在每个 phase 之前。
- **复核修正：**
  - DynamicsUpdate +0x39 只在 phase 1 被消费（`sub_8E4110`，1059659），所以**这一项的时序与 r 无关**。
  - PartitionManager 和 CollisionManager 在 CRC 里只贡献常量，只有 ShroudManager 贡献真实状态（每次 CRC 滚动哈希 1/20 的格子）。
  - 仍与 r 相关的部分：容器乘员二阶移动晚一帧或早一帧；0.01 位移阈值与 +484 首次快照按冲刷窗口计算（窗口被切细后可能少触发或多触发）；r=6 时 phase 1 的移动在同一帧 phase 2 就进入 PartitionManager，phase 4 的移动在同一帧 phase 5 就进入 shroud。
  - 「这条解释了 30 对 90 的实时不同步」属于**推测**。
- **修法：**
  - 把 0x006266F7 的 `call sub_4D5600`（E8，ecx = GL）改指到 wrapper：只有当 `ph == 3 || ph >= 6`（外加开局初值，初值要去 `sub_61B560` / `sub_627A20` 核对）时才调用原函数，否则直接返回。
  - 被挡住时 GL+796 保持 0，表继续累积，+484 仍保留第一份快照，双缓冲切换次数与原版相同。
  - 本轮补读确认，`sub_626620` 入口处 `this[22]` 的取值为：原版 {3, 6, ≥7}；r=4 {2,3,5,6,≥7}；r=6 {1..6,≥7}。
  - 调度必须保证 phase 3 和 phase 6 之后都有客户端帧边界。r=4 与 r=6 满足，**r=3 与 r=5 不满足**，因此目标帧率只能取 30/60/90。
- **修后能否逐位确定：** 冲刷窗口与原版相同。

#### R-4（中，只影响脚本时间冻结）：冻结重试时补跑的 phase 数取决于 r。对应 client-to-sim CH-1，复核 2/3，**三位都做了修正，原始机制被推翻**。

- **修正后的机制：**
  - 脚本动作 0x16 → view vt+120 = `sub_5EACA0`，置 +9749（357202），冻结开始。
  - `sub_4F81F0` 在 phase 1 读 `CDB7B4 vt+156 && !vt+108`。如果冻结且没有 type-1 消息，就置 `CDB750+196=0` 并返回（212758–212776）。
  - `sub_616130` 此时**仍然会跑批次**：本轮补读确认，451093–451104 在调用 phase 1 之后直接进入批次循环，不检查 +196。
  - `sub_6027D0` 随后恢复 `this[22]`，下一帧重试 phase 1。
  - 每个冻结的显示帧：原版补跑 phase 2+3；r=4 只补跑 phase 2；r=6 什么都不补跑（0x616265 `cmp edi,6; jge`）。phase 4–6 在任何配置下都不会跑。
  - 候选影响：phase 2 的管理器，具体是 CollisionManager 在 `sub_9980E0` 里的 onCollide 重派发。影响是推测。
- **修法：**
  - 在 P2 的 `fl_hook_batch(p=1, r)` 中：若 `*(byte*)(CDB750+0xC4)==0`（phase 1 冻结；LABEL_29 的失败路径早已返回，不会走到这里）就返回原版 r=2 的 target 3。
  - r=6 时还要让 0x616265 的 `jge` 不跳过批次块（字节待核）。
- **能否逐位确定：**
  - FL_G_CAMERA **关**时，镜头按显示帧每步 33 ms 推进，冻结持续的显示帧数等于原版，重试次数也等于原版，配合上面的修法可以**精确**回到原版。
  - FL_G_CAMERA **开**时，冻结持续约 3N 个显示帧。要对齐原版，只能在「累计镜头毫秒跨过 33 ms 边界」的那一帧补跑，边界舍入可能差 1，**无法保证逐位确定**。
  - 推测：原版联机里，`sub_602720` 在 `this[22]>6` 且下一帧数据已到时会跳过 GameClient::update，镜头就不前进，冻结难以结束。这与 Generals 源码里「@todo make sure this never happens during a network game」一致。这条路很可能只出现在战役或合作的过场。

#### R-5（低，对模拟而言基本只是客户端问题）：M3，R1 站点 `sub_5FFAD0`（`phase == 6/r`）

- r=4 时帧开头的 phase 只可能是 {6,2,3,5}，而 6/4=1，所以这个测试**永远不成立**，`GhostObjectManager::update`（`sub_715070`）在 60 帧下从不执行。r=6 时它在 phase 1 之后成立。
- 各调用者（`sub_542DF0`、`sub_602720`、`sub_6293D0`、`sub_70F350`）都在客户端或节拍控制侧（PS-2 复核）。它是否会通过 `sub_992DF0` 取消看见、从而改动受 CRC 的 shroud 格子，是推测。
- **修法：** 把 0x5FFAD0 移出 R1 改指集合，让它保持 r=2 语义，也就是测 phase==3。r=4 与 r=6 下它都会在每个逻辑帧 phase 3 之后成立一次，与原版一致。

#### R-6（未知，最大的剩余缺口）：`sub_626620` 里其它逐客户端帧执行的工作还没审完

### 1.3 源 I / 源 II 的对应关系（全部推测）

| 实测 | 最可能的机制 | 为什么吻合 | 反例风险 |
|---|---|---|---|
| 源 I（约 2400 帧，只在 bit0 RATIO 开时） | R-2（M1 删除移位）、R-3（M2） | 只在 r>2 时出现；phase 6 的销毁要赶上 CRC 帧才会暴露，属于偶发事件 | M1 本身无对抗复核 |
| 源 II（约 10800 帧，与 bit0 无关） | R-1（DG-1） | 所有 desync 臂都开着 DERIVED2；目标 30 时值为 30，与原版一致，正好对应「补丁 30 帧跑满 16886 帧」 | 游泳步兵下水是常见动作，10800 帧才出现可能偏晚。分歧是暂时的，要和 CRC 间隔重叠才会被发现 |
| 实时对局 30 原版 对 90 补丁 | R-1 + R-2 + R-3 同时存在 | —— | —— |

### 1.4 三种总体方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **B（推荐，改动最小）** | RATIO 保持开；R-1 固定为 30；R-2 / R-3 加边界门；R-5 移出 R1；R-4 在 P2 里模拟原版补跑；R-6 逐项审 | 现有视觉修复体系（都假设显示帧号按目标帧率走）不用动 | 完整性取决于 R-6 的清单 |
| **C（结构性保证）** | 模拟调度固定按 r=2 分组；多出来的显示帧做成「只渲染帧」：补丁自己的节拍门决定何时允许进入 phase 1，同时补丁自己推进显示帧号，覆盖 `sub_602720` 的跳过与降速，重算插值系数 | `sub_626620` 的所有延迟工作按构造都落在原版边界上 | 改动大；显示帧号自己推进之后，要重新审「没有模拟读者读显示帧号」（CH-5 的普查说没有，但无复核）；联机时 `sub_602720` 在 `this[22]>6` 分支会跳过渲染并降速 |
| **A（F5 原样：只把 RATIO 关掉）** | 只作**实验臂**，不作为产品方案 | —— | 显示帧号退回 30 Hz，整套视觉修复失准，PSYS 节拍门会降到约 10 Hz（推测）；单机实时对局里 phase 1 没有计时门，逻辑可能跑到 30/45 Hz（推测，§1.1） |

### 1.5 能修、原则上修不了、只能实测

- **能修，并且可以离线自证：**
  - R-1：3 个操作数；
  - R-2 / R-3：两个 call 的 wrapper 加谓词 `ph==3 || ph>=6`；
  - R-5：从 R1 改指集合中剔除；
  - R-7：安装时拒绝；
  - R-4 在 FL_G_CAMERA 关时的精确版本。
- **原则上保证不了：**
  - ① 静态分析证明不了清单完整：虚函数边、没解析出来的 hub 管理器（`CDB71C+268`、`CDB794`、`CDB79C`、`CDB7B4`、`CE3F14`、`CE9810`、`CEBD4C`、`CEDFA0`）。
  - ② R-4 在 FL_G_CAMERA 开时，重试次数取决于本机镜头推进的边界舍入。
  - ③ 原版自己也不确定的东西：phase 1–3 读时钟、mod 里的 Lua `random`。
  - ④ 「30 原版 + 补丁」这种组合，要求补丁侧逐位复现原版，以后每加一个位都要重跑 determinism。
- **只能实测：**
  - DG-1 是不是源 II；
  - M1/M2 是不是源 I；
  - RA3 的 Object CRC 是否包含变换；
  - 修完以后能否跑完整份录像；
  - 实时同场。

## 3. 其它仍存在的 60/90 帧视觉问题

1. **电厂 / 矿场的光还剩大约 3 倍**（HANDOFF §24.4、§26）。本轮的 8 个维度都没有专门查它。现有线索：
   - **(a) 先确认节拍门是否真的装上了：** 查那一局日志里「粒子系统节拍门已生效(放行比例 N/1000)」的 N 是否约等于 333。
   - **(b) 新线索（本轮补读）：** `fl_wrap_psys` 的虚拟帧取自显示帧号，而显示帧号只在 `CDB750+196` 置位的帧才推进。RATIO 关时它是 30 Hz，节拍门只会放行约 1/3，粒子更新会**变慢**到约 10 Hz（推测，没测过）。所以这条解释不了「偏快」，但 bit0 关时会出问题。
   - **(c) 节拍门只管更新，不管创建。** 本轮补读 `sub_6D1DC0` 的调用者，绘制侧有 `sub_908780`（ParticleSysBone 挂接 / 重建，dump 1089500–1089520：同一骨骼上没有存活系统时就新建一个，并立即 `sub_6BEE40`）、`sub_8FB3A0`、`sub_90A030`（构造函数，一次性）。如果 SovietPowerGlow 的系统寿命有限、死掉后由 `sub_908780` 按显示帧检查并立即重建，每次重建又自带初始爆发，那么爆发频率与节拍门无关。**推测**。下一步：静态读 `sub_908780` 的调用节拍和删除条件；实测按模板名统计 `sub_6D1DC0` 与 `sub_6BF1F0` 每秒的次数，30 与 90 各测一次。
   - **(d)** `sub_6D1B70(CE3F04)` 在 `sub_626620` 里每客户端帧执行一次，不在节拍门后面。它排空的是一个延迟操作队列（case 0–4：`sub_6CAA60`、`sub_6C7A90`、`sub_6D1260(sys,1)`、音频 `CDD308`），不是递减计数器。低概率原因，但生产者没查。
   - **已排除：** GPU 粒子的 age 用的是着色器常量 30（本轮补读）；FXGLOWS2 / FX_LIGHTS 网格走游戏时钟（§24.4）。
   - **测量：** §24.4 的亮度频谱，三臂（原版 30 / 90 勾选 / 90 不勾选）。
2. **R-5 的视觉后果：** 60 帧下 `sub_5FFAD0` 永远不成立，于是 GhostObjectManager 的清理从不执行（迷雾中的幽灵对象可能残留，属于泄漏风险），`sub_53A730` 的每逻辑帧 drawable 快照也被停用。90 帧下它在逻辑帧中途执行。修法同 R-5。
3. **`sub_7C9990` 的染色保持时间只剩 1/2 或 1/3**（caf9d4 F4）：保持时间 = `(CAF9D4/CAF9D0)×逻辑帧`，而攻击和衰减用的是 `flt_CDBC50`。它走的是 `sub_6D7520 → sub_51B0C0`，**不经过** FL_G_TINT 包的 `sub_529450`，所以没有被修到。修法：改指 0x7C9A5A / 0x7C9A62，或者在 `sub_6D7520` 里缩放 a5。
4. **R4 隐身脉动**的首次过渡会出现一帧负值不透明度毛刺（`sub_532AC0`，caf9d4 F5）。
5. **`CE3B18 = 900` 显示帧的定时 flush**（`sub_67B580` → `sub_6764C0`，疑似在线遥测）在 60/90 帧下变成 2 倍 / 3 倍频率（caf9d4 F6）。
6. **39 个 `CAF9D4>>1 = 15` 的全局**（普查原记 7 个）的读者没审。只有与显示帧号混用的读者才会造成视觉速率问题。
7. **记忆中已登记的未修项：** 天气闪电、Drawable 染色闪白、浮动文字、消息行淡出、右键拖拽卷屏 `sub_ABFF40`。
8. **警告：** 如果采用方案 C 或 A，显示帧号的节奏会改变，DERIVED2 / P6b / CAMERA / TINT / PSYS 以及各种节拍门的换算前提都要重审。
